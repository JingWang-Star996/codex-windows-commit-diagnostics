# 缓解 Windows 版 Codex 运行期间的系统提交内存持续增长

**简体中文** · [English](README.en.md)

如果使用 Microsoft Store 版 Codex 桌面应用时，任务管理器里的**「已提交」持续上涨**，先确认增长来自哪里。在一台 Windows 机器上，Codex 通过目录联接访问桌面资料时反复重试，NTFS 的 `NtFC` 非分页池随之增长。退出 Codex、把实体资料目录移回包私有位置后，这部分增长明显放缓。下面的只读检查器和离线指南可以帮助你判断自己的机器是否适用，并在需要时回退。

**这次缓解取得了什么效果？** 在这台机器上，旧布局的一小时内 `NtFC` 增长约 **6.83 GiB**，调整后的首小时仅增长约 **0.197 MiB**。这两个数都是内核池标签的增量。先前积累的约 **15.24 GiB** 仍然驻留。

判断是否适用时，先看两个条件是否同时成立。日常负载下，`NtFC` 字节数持续增长，且下方检查器返回 `match`。只有两个条件都满足，才考虑离线缓解。若整机提交继续上涨而 `NtFC` 持平，应另查进程私有提交等来源。[下载 v0.1.0](https://github.com/JingWang-Star996/codex-windows-commit-diagnostics/releases/tag/v0.1.0)

## 运行

在本目录打开终端，以普通用户运行。需要 Windows 10/11、Windows PowerShell 5.1 和 Python 3.11 或更高版本，无第三方 Python 依赖。

```powershell
python -I -B diagnose.py
python -I -B diagnose.py --plan
python -I -B tests.py
```

前两条命令只向终端输出 JSON。默认检查本用户已注册的 Store 包和固定的两个路径。`--plan` 在命中旧布局时附上诊断和离线处置要点。检查器不打开资料文件，不遍历目录树，也没有修改目录、结束进程、上传数据或自动修复的入口。最后一条命令在临时目录运行测试。

| 输出 layout | 含义 | 后续动作 |
|---|---|---|
| match | 包私有位置是直接指向公共实体目录的 NTFS 联接，符合历史布局 | 在日常负载下核对 NtFC 增量及应用活动，再评估离线处置 |
| native | 公共名称空缺，包私有位置是普通目录 | 当前布局与迁移后的外观相容；仅凭这两项无法确认过去做过修复 |
| indeterminate | 注册、路径、权限、卷、拓扑或两次读取的一致性未满足条件 | 保持现状；检查当前安装方式以及其他内存来源 |

退出码 0 表示获得可分类的布局，2 表示无法分类或参数无效。旧布局命中时同样返回 0，命中只描述磁盘布局。

## 哪个计数器在涨？

Windows 任务管理器“性能 → 内存”的“已提交”是**整机**的提交量及限额。进程的 **Private Bytes / 提交大小**度量该进程的私有提交。**Working Set / 工作集**度量当前驻留在 RAM 中的页面，其中可含共享页。进程退出时，进程私有提交和工作集可以下降，同时先前积累的内核池仍然驻留。

这个案例跟踪的是 **NtFC 非分页池标签的字节数**。可以用微软的 PoolMon 在同等日常负载下间隔观察该标签的 Bytes，记下时间及差值。同时记录主机提交量、非分页池总量和相关进程的 Private Bytes。单次高点或非分页池总量不能替代 NtFC 的时间序列。只观察现有负载，不需要制造内存压力。[微软 PoolMon 说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/poolmon) · [微软进程内存计数器](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)

## 单机观察

原桌面程序在包身份下更新资料文件时反复遇到改名失败，随后重试。11 月 19 日将实体资料目录移回包私有位置并正常重开一次。两个观察窗口的 NtFC 增量如下。

| 窗口 | NtFC 非分页池标签变化 |
|---|---|
| 旧布局历史一小时 | 约 +6.83 GiB |
| 调整后第一小时 | 约 +0.197 MiB |
| 调整后至 2 小时 16 分 | 累计仍约 +0.197 MiB |
| 次日上午，相较前晚复核 | +8,320 字节 |

调整前约 15.24 GiB 的该标签占用仍然驻留。次日整机提交再次升高，NtFC 同期仅有很小增量。证据支持这台机器上的缓解效果，尚未验证跨版本效果或定位上游实现责任。

## 离线人工缓解

下面记录已验证的操作顺序。只有输出为 match、日常观测支持同类现象、能够独立核对文件身份并恢复备份时才适用。共享电脑、重定向的用户配置、跨卷目录、其他安装渠道及不同的联接拓扑都不在这次验证范围内。

| 角色 | 初始状态 |
|---|---|
| P — 公共资料名 | `%APPDATA%\Codex`，包含当前资料的实体目录 |
| Q — 包私有资料名 | `%LOCALAPPDATA%\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Roaming\Codex`，直接指向 P 的目录联接 |
| R — 保留旧联接的名字 | 在 Q 的父目录新选的未使用名称，包括断开的联接也算占用 |

上表中的环境变量是路径简写。检查器使用 Windows 当前用户的 Known Folder 实际位置。在包外核实 RoamingAppData 和 LocalAppData 两个位置；若环境变量、包内视图或手工打开的位置与实际位置不一致，请停止操作。

1. 保存工作，手动退出桌面应用和使用这份资料的辅助进程，确认进程没有自动重启。用可信的备份方式单独保存完整资料，确认能够恢复，妥善保护其中的个人数据。备份不应放在 P、Q 或 R 内。
2. 在包外的普通终端记录当前用户的包身份、P 的卷与文件 ID、Q 的卷与联接自身文件 ID、联接的直接目标和所选 R。核实两个路径的祖先均为普通本地目录，父目录在同一 NTFS 卷。不要只看相同的盘符、快捷方式图标或联接跟随后的显示结果。核对有困难时停在此处。
3. 只重命名 Q 处的**联接本身**，同一父目录内改称 R。核对 R 仍是同一联接、目标仍是 P，Q 名称已腾空，P 的实体身份未变。
4. 以同卷改名方式把**实体 P** 移到 Q。再次核对 P 名称空缺、Q 是普通目录且保留原 P 的文件 ID。R 此时仍指向旧名称 P，目标暂时不存在。跨卷复制、覆盖和合并会使这套回退条件失效。
5. 手动重开 Codex，确认既有资料和新写入可用。记录日常负载下重开初期及约一小时后的 NtFC 增量，并同整机和进程计数对照。重新运行检查器通常应得到 native。保留备份、R 与操作记录，直到资料和增长趋势都已复核。

### 中断和回退

| 现场情况 | 核对后采取的动作 |
|---|---|
| 第一步改名已完成，P 仍是原实体、Q 空缺、R 是原联接 | 保持应用离线，直接把 R 改回 Q，再核实 Q 的目标和两者身份 |
| 两步均完成，需要完整回退 | 再次退出应用、保护 Q 中最新写入。确认 P 仍空缺、Q 是同一实体、R 是原联接。先将当前 Q 同卷移回 P，再将 R 改回 Q。核对文件身份、联接目标和新写入 |
| P 重新出现、某个 ID 变化、只找到部分对象、备份不完整，或观察期间又有写入 | 保留所有现状及最新资料；根据实际操作记录和备份单独核对 |

`native` 只从 P 和 Q 得出，不能用作回退授权。回退还需要原备份、独立保留的联接和身份记录。

## 公开案例

- 2026-11-01，另一位用户报告 Codex 的 Store 包在重定向的 AppData 目录上伴随 NtFC 增长。调整布局后增长放缓。其原来有两个不同目标，不能把本页的两步迁移推广到那个布局。[openai/codex #58641](https://github.com/openai/codex/issues/58641)
- 2026-10-21，报告者用 PoolMon 观察到退出 Codex 后 NtFC 增长停止，先前占用持续驻留；报告未证实这里的目录关系。[openai/codex #55812](https://github.com/openai/codex/issues/55812)
- 2026-07-06，另一台机器的持续占用主要集中在文件对象和 I/O 等多个内核标签。8 月的另一起报告根据系统事件将大量提交直接归于 codex.exe。两个测量对象不同。[openai/codex #31212](https://github.com/openai/codex/issues/31212) · [openai/codex #38765](https://github.com/openai/codex/issues/38765)
- 2026-11-24，桌面版重试图片队列时进程树观测约 6 GB。报告没有注明内存计数器，无法据此判断是否属于同一问题。[openai/codex #63592](https://github.com/openai/codex/issues/63592)

本工具为独立整理的诊断和人工缓解资料。测试使用合成目录验证判断、干跑和回退流程。对内核增长的实测来自上面的一次历史处置。
